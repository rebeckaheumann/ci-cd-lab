# CI/CD 实践学习计划

本目录用于从零搭建一个完整的 CI/CD 实验项目。学习方式以实践为主：每次只引入一个新概念，先在本地验证，再接入自动化流水线。

## 技术栈

- Python
- pytest
- GitHub Actions
- Docker
- 后续根据需要选择部署平台

## 最终目标

完成下面的交付链路：

```text
提交代码
  → 触发 CI
  → 安装依赖
  → 代码检查
  → 自动测试
  → 构建制品和容器镜像
  → 发布镜像
  → 部署测试环境
  → 部署后验证
  → 批准并部署生产环境
  → 必要时回滚
```

## 学习原则

1. 每次只增加一个自动化环节。
2. 命令必须先在本地运行成功，再放入 CI。
3. CI 流水线应快速、稳定，并在错误发生时明确失败。
4. 构建一次，部署同一个不可变制品；不在不同环境重复构建。
5. 密钥不得写入代码、镜像或仓库，统一通过 Secrets 管理。
6. 每次部署后执行健康检查或 smoke test。
7. 每个阶段都保留一个可运行、可验证的结果。
8. 暂不引入 Kubernetes；先掌握 Git、测试、制品、Docker 和基础部署。

## 互动学习方式

1. 每个短流程开始前，先讲解必要概念、目标和验收标准。
2. 实践阶段只描述要完成的结果和约束，不直接给出可复制执行的命令。
3. 学习者自行判断应使用的工具和命令；遇到问题时可以随时提问。
4. 与当前知识点无关的机器环境配置由助手处理。
5. 每个阶段性任务完成后，由助手检查文件、运行实际程序并按既定标准验收。
6. 验收失败时，先说明现象和原因，再给出逐级提示；不直接替代学习者完成任务。
7. 不使用 OMP Todo 跟踪等待学习者操作、提问或验收的教学步骤，避免产生无意义的未完成提醒。

## 阶段一：创建最小应用

状态：未开始

### 学习内容

- Python 项目结构
- 依赖管理
- 命令退出码
- 单元测试基础
- Git 基本工作流

### 实践任务

- [ ] 创建一个最小 Python Web 服务
- [ ] 添加健康检查接口
- [ ] 使用 pytest 添加自动化测试
- [ ] 添加代码格式和静态检查工具
- [ ] 提供统一的 `lint`、`test`、`run` 命令
- [ ] 初始化 Git 仓库并创建首个提交

### 完成标准

- 应用可以在本地启动。
- 健康检查接口返回成功状态。
- 测试可以在本地稳定执行。
- 故意破坏功能时，测试必须失败并返回非零退出码。

## 阶段二：接入持续集成 CI

状态：未开始

### 学习内容

- Workflow、Job、Step 和 Runner
- `push` 与 `pull_request` 触发器
- Job 依赖关系
- CI 日志和失败诊断
- 依赖缓存

### 实践任务

- [ ] 创建 GitHub Actions CI Workflow
- [ ] 在 CI 中安装固定版本的 Python
- [ ] 安装项目依赖
- [ ] 执行代码检查
- [ ] 执行自动化测试
- [ ] 配置依赖缓存
- [ ] 制造一次失败并根据日志定位原因

### 完成标准

- 每次 push 和 pull request 都会触发 CI。
- 检查或测试失败时，Workflow 必须失败。
- 只有所有检查通过的提交才允许进入下一阶段。

## 阶段三：构建和管理制品

状态：未开始

### 学习内容

- Build Artifact
- Job 之间传递制品
- Git SHA、Tag 和版本号
- 可重复构建

### 实践任务

- [ ] 为应用添加打包命令
- [ ] 在 CI 中生成构建制品
- [ ] 上传并下载 Workflow Artifact
- [ ] 使用 Git SHA 标识构建结果
- [ ] 使用 Git Tag 标识发布版本

### 完成标准

- 测试通过后才能构建制品。
- 构建结果可以从 CI 下载。
- 每个制品都能追溯到唯一的 Git Commit。

状态：未开始

### 学习内容

- Dockerfile
- 构建上下文和 `.dockerignore`
- 镜像层与缓存
- 多阶段构建
- 非 root 用户
- 容器健康检查

### 实践任务

- [ ] 编写 Dockerfile
- [ ] 添加 `.dockerignore`
- [ ] 使用非 root 用户运行应用
- [ ] 构建并运行本地镜像
- [ ] 验证容器健康检查
- [ ] 在 CI 中构建镜像
- [ ] 使用 Git SHA 和版本号标记镜像

### 完成标准

- 应用可以完全通过容器运行。
- 容器不依赖本地源代码挂载。
- 镜像具有可追溯且不可变的版本标签。
- 容器以非 root 用户运行。

## 阶段五：镜像发布

状态：未开始

### 学习内容

- Container Registry
- Secrets 与普通配置
- 最小权限令牌
- 镜像标签策略

### 实践任务

- [ ] 选择并配置容器镜像仓库
- [ ] 将认证信息保存为 GitHub Secrets
- [ ] 在 CI 中登录镜像仓库
- [ ] 推送 Git SHA 镜像标签

### 完成标准

- 认证信息不出现在仓库和日志中。
- Registry 中的镜像可以追溯到对应 Commit。
- 可以在一台没有项目源代码的环境中拉取并运行镜像。

## 阶段六：部署到测试环境

状态：未开始

### 学习内容

- Development、Staging 和 Production 环境
- 配置与代码分离
- 持续部署
- 健康检查和 smoke test

### 实践任务

- [ ] 创建 staging 环境
- [ ] main 分支通过 CI 后自动部署 staging
- [ ] 通过环境变量注入配置
- [ ] 部署后执行健康检查
- [ ] 部署后执行 API smoke test
- [ ] 验证部署失败会导致 Workflow 失败

### 完成标准

- main 分支的合格版本可以自动部署 staging。
- staging 使用 CI 构建并发布的同一个镜像。
- 部署后验证失败时，流水线不得显示成功。

## 阶段七：生产发布和回滚

状态：未开始

### 学习内容

- 持续交付与持续部署的区别
- Git Tag 发布
- Environment Approval
- 回滚策略
- 滚动、蓝绿和金丝雀发布的基本思想

### 实践任务

- [ ] 使用版本 Tag 触发生产发布流程
- [ ] 添加生产环境手动批准
- [ ] 将 staging 验证过的镜像部署到 production
- [ ] 保存上一稳定版本信息
- [ ] 故意部署一个坏版本
- [ ] 回滚到上一稳定版本
- [ ] 验证回滚后的服务状态

### 完成标准

- 没有批准时不能部署 production。
- production 不重新构建镜像。
- 可以明确选择一个历史版本并完成回滚。
- 回滚后必须执行健康检查和 smoke test。
